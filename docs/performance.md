## 2. 읽는 법과 한계

- **1500장 약 1분(6개 병렬).** 병렬을 1개로 줄이면 약 6분이다. 메모리가 부족하면 `--workers`로 줄일 수 있다.
- **메모리는 프로세스당 약 600MB**(얼굴 검출 프레임워크 포함)이고, 병렬 개수에 비례한다. 값은 프로세스별 상주 메모리의 합이라 공유되는 부분이 겹쳐 세어져 **실제보다 크게 나온다.**
- **디스크 캐시가 데워진 상태의 값이다.** 1500장 측정은 375장을 4번 반복해 만든 것이고(심볼릭 링크), 같은 파일을 다시 읽으므로 첫 읽기보다 빠를 수 있다. 사진은 평균 24MB라 1500장이면 약 36GB를 읽는다. 내장 SSD(초당 1GB 이상)면 읽기만 약 30초 안쪽이지만, **외장 드라이브나 네트워크 드라이브에서는 읽기가 병목이 될 수 있다.** 실제 행사 폴더를 처음 읽는 조건의 시간은 새 행사에서 확인해야 한다.
- 이 MacBook 기준이다. 실제로 쓸 iMac(PRD의 대상 기기)에서는 사양에 따라 달라진다.
- 리포트 HTML은 썸네일을 모두 넣으면 1500장에 21MB다. 브라우저에서 여는 속도는 이번에 재지 않았다. 부담되면 `--thumbs flagged`로 후보·확인·판정 불가만 넣는다.

## 3. Q4(1500장 분석 허용 시간)와 비교

**Q4는 3분 이내로 확정되었다 (2026-10-19).** 측정값은 6개 병렬 약 1분, 3개 병렬 약 1.9분이라 충족한다. 외장 드라이브·iMac에서는 새 행사로 다시 확인한다. 검토했던 선택지:

| 선택지 | 의미 |
|---|---|
| 5분 이내 | 여유 있게 충족. 병렬을 1개로 줄여도 겨우 넘는 수준이라 메모리가 모자란 기기에서도 가능 |
| 3분 이내 | 6개 병렬(약 1분)이면 외장 드라이브에서도 대체로 충족, 병렬 3개(약 2분)도 충족 |
| 1분 이내 | 이 MacBook의 데워진 캐시 조건에서만 겨우 충족. 첫 읽기·다른 기기에서는 어긋날 수 있음 |

## 4. Capture One 연동 (`apply`, `rollback`) — T2.9 실측 (2026-10-19)

시험용 카탈로그 `bcut-test-400`(행사 A 400장, 후보 32 + 확인 28 = 60컷, 붙인 키워드 120건), 이 MacBook.

| 작업 | 시간 | 비고 |
|---|---|---|
| 카탈로그 읽기(`list_variants`) | 13.2초 | 장당 33 ms. 대부분의 시간 |
| `apply` dry-run | 12~14초 | 읽기 1번 |
| `apply --commit` | 28초 | 카탈로그 백업 + 읽기 2번 + 키워드 120건 |
| `rollback` dry-run | 19초 | |
| `rollback --commit` | 33초 | 읽기 2번 + 키워드 120건 제거 |

**맥이 바쁠 때는 2~3배 느려진다**(리허설: `apply --commit` 86초, `rollback --commit` 52.6초, 같은 읽기가 12.8초와 32.8초로 요동, [rehearsal-report.md](rehearsal-report.md)). 아래 환산은 한가한 맥 기준이며, 바쁠 때는 apply 약 5분, rollback 약 3.3분으로 3분 기준을 넘을 수 있다.

**1500장 환산(추정, 직접 측정 아님):** 읽기가 장당 33 ms로 장수에 비례한다고 보면 한 번 읽는 데 약 50초, `apply --commit`은 읽기 2번 + 반영 컷 약 225개 처리로 **약 2분**, `rollback --commit`은 **약 2~2.5분**이다. Q4(분석 3분 이내)는 분석(`scan`) 기준이고, 연동은 **`apply`·`rollback` 각각 3분 이내**로 따로 확정했다(Q10). 추정치는 둘 다 기준 이내이지만 rollback은 여유가 약 20%로 작다.
한계: 사진이 545장뿐이라 1500장은 직접 재지 못했다. 읽기 시간이 장수에 정확히 비례하는지는 확인하지 못했다.
