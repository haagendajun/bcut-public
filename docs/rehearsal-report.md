# 리허설 보고 (T3.5)

실시: 2026-10-19. 대상: 행사 A 400장(복제본), 카탈로그 `bcut-test-400`(시험용), 이 MacBook. **개발자(Claude)가 런북의 명령을 순서대로 실행했다.** 처음 쓰는 사람이 한 것이 아니므로 T3.2의 완료 기준("처음 쓰는 사람이 런북만 보고 `scan`부터 `rollback`까지")은 **아직 확인하지 못했다.**

## 1. 단계별 결과와 시간

| 런북 단계 | 결과 | 시간 |
|---|---|---|
| ② `scan` (400장) | 후보 32 / 확인 28 / 정상 328 / 얼굴 없음 12, 사유별 눈 감김 58·흔들림 2. 결과 3개 파일 생성 | 22.8초 |
| ③ 리포트 확인 (HTML) | **하지 않음** (파일 생성만 확인, 5.7MB) | - |
| ④ `apply` 미리보기 | 반영 대상 60장(15%), 찾음 60·못 찾음 0, 붙을 키워드 4종 | 38.6초 |
| ④ `apply --commit` (카탈로그 백업 포함) | 60컷에 키워드 120건, 별점·태그 변화 0 | 86.0초 |
| ⑤ `albums` 미리보기 / `--commit` | 앨범 8개 생성 | 0.4초 / 1.7초 |
| ⑥ Capture One에서 확인하고 제외 | **하지 않음** — 사용자가 화면 조작 방법을 몰라 건너뛰기로 함 (아래 발견 1) | - |
| 6장 `rollback` 미리보기 / `--commit` | 60컷에서 키워드 120건 제거, **시작 상태와 동일**(키워드·별점 확인, 앨범 장수도 기대와 일치) | 27.5초 / 52.6초 |

시작 상태와 되돌린 뒤 상태가 같음: 이 카탈로그에는 처음부터 키워드 4개가 붙은 컷 4장(PHA_7983~7986, 키워드를 만들면서 붙은 것)이 있었고, rollback 뒤에도 그대로였다.

## 2. 발견한 것 (런북 수정으로 이어진 것)

1. **런북 ⑥이 사람 기준으로 불충분했다.** "후보 앨범을 열고 좋은 컷에 별점을 준다"만 적혀 있어서, 사용자가 Capture One에서 어떻게 하는지 몰라 단계를 건너뛰었다. 앨범이 왼쪽 어디에 있는지, 별점을 어떻게 주는지, 무엇을 보고 판단하는지가 없었다 → 런북 ⑥에 구체적인 방법을 추가했다.
2. **시간이 크게 흔들린다.** 같은 `apply` 미리보기가 지난번 12~14초였는데 이번에는 38.6초, `commit`은 28초 → 86초였다. 같은 카탈로그 읽기가 32.8초와 12.8초로 요동쳤다. 시험 당시 맥이 영상 인코딩 프로세스 때문에 바빴다(부하 평균 3.7~5). **무거운 작업이 도는 맥에서는 연동 명령이 2~3배 느려진다.** 아래 3장과 런북에 반영했다.
3. 모든 명령이 오류 없이 끝났고, 안내문(중단 사유, 다음 행동)도 필요하지 않았다. 처음 실행하는 사람이 겪을 오류(키워드 없음, 카탈로그 다름 등)는 이번 리허설에서는 나오지 않았다(앞선 시험에서 확인).

## 3. 1500장 시간에 대한 영향 (3분 기준, Q10)

400장 실측을 장수에 비례해 1500장으로 환산한 추정이다.

| | 400장 조용할 때 | 400장 바쁠 때(이번) | 1500장 환산 (조용 → 바쁨) |
|---|---|---|---|
| `apply --commit` | 28초 | 86초 | 약 2분 → **약 5분** |
| `rollback --commit` | 33초 | 52.6초 | 약 2~2.5분 → **약 3.3분** |

**3분 기준은 맥이 조용할 때만 충족될 것으로 추정된다.** 바쁜 맥에서는 `apply`가 기준을 크게 넘을 수 있다. 대응: ① 행사 처리 때 영상 통화·인코딩 같은 무거운 작업을 끈다(런북에 적음), ② 카탈로그를 두 번 읽는 부분을 대상 컷만 읽도록 줄이는 개선(G2 조건 6)을 우선한다.
