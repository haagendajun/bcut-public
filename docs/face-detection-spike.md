# T1.3 스파이크 결과: 얼굴·눈 랜드마크 라이브러리

> 실행일: 2026-10-19 · 입력: T1.2에서 정한 경로 (CR3 내장 JPEG, draft 2048)
> 코드: [tools/spike_t13_vision.py](../tools/spike_t13_vision.py) (스파이크 전용 가상환경에서 실행)
> 사진은 읽기만 했고, 사람이 열어 보지 않고 숫자 지표만 계산했다. 네트워크 사용 없음.

## 1. 결론

**macOS Vision(`VNDetectFaceLandmarksRequest`, pyobjc 경유)을 기본 얼굴·눈 판정기로 채택한다.** 다른 후보를 시험하지 않고도 요구를 충족했다.

| 항목 | 결과 |
|---|---|
| 설치 | Python 3.13에서 `pyobjc-framework-Vision`, `pyobjc-framework-Quartz` 설치 성공 |
| 모델 다운로드 | **필요 없음** (macOS에 내장). 사진 반출 걱정 없음 |
| 속도 (1장) | **Vision 7~9 ms** (읽기 46 ms 포함 약 55 ms). 1500장 약 1.5분 이내 [추정] |
| 눈 랜드마크 | 눈마다 **윤곽 6점** (눈 종횡비 계산에 충분) |
| 얼굴 검출 (EVENT_A 147장) | 눈 감김 47/47, 표정 주의 40/40, 정상 58/60 (97%) |
| 얼굴 검출 (EVENT_B 138장) | 눈 감김 1/1, 표정 주의 21/21, 정상 106/116 (91%) |
| 눈 폭 (풀 해상도 기준) | EVENT_A 중앙값 약 85 px, EVENT_B 약 150 px. 분석 입력(2048px)에서는 약 21 px와 약 38 px |

## 2. 후보별 시험 현황

| 후보 | 시험 | 결과 |
|---|---|---|
| **macOS Vision (pyobjc)** | **완료** | 위 표. 채택 |
| MediaPipe Face Landmarker | **보류** | `pip` 설치는 됨(1.1.1). 하지만 이 버전에는 예전 `solutions` 방식이 없고, 새 방식은 **모델 파일(`face_landmarker.task`)을 따로 내려받아야 한다.** 사용자 허락이 필요하고, Vision이 충분해서 필요성이 낮다 |
| OpenCV | **시험 안 함** | 설치는 됨(5.0). 기본 포함 Haar 눈 분류기는 눈 상자만 주고 윤곽 랜드마크가 없어 눈 감김 판정에 부적합. 윤곽을 주는 모델은 따로 내려받아야 한다 |
| dlib (68점) | **시험 안 함** | C++ 빌드 도구가 필요하고 모델 파일(약 100 MB)을 내려받아야 해서 비용 대비 이득이 없다 |

> 이후 Vision이 다른 사진(다른 사진가, 다른 카메라)에서 약하면 MediaPipe를 그때 시험한다 (모델 다운로드는 사용자 확인 후).

## 3. 눈 감김 분리력 (EVENT_A, 이 표본에서의 참고치)

> **임계값을 튜닝한 것이 아니다.** 눈 열림 비율(눈 윤곽의 세로 ÷ 가로, 두 눈 중 더 감긴 쪽)이 B와 나머지를 얼마나 가르는지만 본 것이다. 주 얼굴 = 가장 큰 얼굴. 표본은 B 47, 표정 주의 40, 정상 58.

| 비교 | AUC | 오탐 0%에서 재현율 | 오탐 1%에서 | 오탐 5%에서 |
|---|---|---|---|---|
| B vs 정상 | **0.999** | **94%** | 100% | 100% |
| B vs **표정 주의** | 0.969 | **45%** | 60% | 85% |
| B vs 정상 + 표정 주의 | 0.987 | 45% | 72% | 94% |

**눈 열림 비율 분포 (주 얼굴, 낮을수록 감김)**

| 라벨 | p10 | 중앙값 | p90 |
|---|---|---|---|
| 눈 감김 (B) | 0.076 | 0.114 | 0.152 |
| 표정 주의 | 0.156 | 0.238 | 0.297 |
| 정상 | 0.253 | 0.295 | 0.331 |

해석:
- **정상 컷과는 거의 완벽히 갈린다.** B의 90%가 0.152 이하, 정상의 90%가 0.253 이상이다.
- **어려운 곳은 표정 주의 컷이다.** 이 분포가 B와 정상 사이의 구간(약 0.15~0.30)에 걸쳐 있다. 오탐 0%를 요구하면 표정 주의가 있는 상황에서 재현율이 절반 이하로 떨어진다. 예상한 대로의 결과다.
- 그래서 **분류를 두 단계로 나누는 설계가 맞다는 증거**다: 비율이 충분히 낮으면 `candidate`, 중간 구간은 `review`, 높으면 정상 (devplan 1-F의 "확신도 낮으면 review").
- EVENT_B에서는 B가 1장뿐이라 분리력 숫자는 의미가 없다 (1장). 다만 분포 방향은 같다: 정상 중앙값 0.304, 표정 주의 0.249, B 0.084.

## 4. 한계와 위험

| # | 내용 | 대응 |
|---|---|---|
| 1 | **분리력은 같은 행사에서 같은 사람들을 찍은 표본**이다. 새 행사·새 인물에서는 달라질 수 있다 | 홀드아웃(H)과 블록 교차 검증으로 확인한다 (recall-eval-plan 10장) |
| 2 | ~~주 얼굴만 평가했다~~ → 이 스파이크 시점의 한계. **이후 단체 사진 정책이 확정**됨 (비슷한 크기 얼굴을 모두 보되 후보는 확인으로, [group-photo-policy.md](group-photo-policy.md)) | 해결 |
| 3 | **Vision은 Apple 내부 모델이라 macOS 업데이트로 결과가 바뀔 수 있다** | 임계값은 macOS 버전에 묶는다. macOS가 바뀌면 회귀 평가(T4 회귀)를 다시 돌린다 |
| 4 | **macOS 전용 의존성**이 생긴다 | 이미 Capture One과 AppleScript로 macOS 전용이라 영향 없음 |
| 5 | **잘못 쓰면 프로세스가 죽는다.** Vision 좌표 목록은 길이를 모르는 포인터라서 개수 없이 읽으면 `SIGBUS`로 종료됐다 (이번 시험에서 실제로 발생) | 항상 `pointCount()` 만큼만 읽는다. 읽기 코드를 한 곳에 모으고 테스트한다. 큰 배치는 작업 프로세스를 나눠 한 장의 충돌이 전체를 멈추지 않게 한다 [제안] |
| 6 | **얼굴을 못 찾은 정상 컷** (EVENT_A 2/60, EVENT_B 10/116)은 얼굴 판정 대상이 아니다 | 이런 컷은 눈 감김 판정 없이 정상으로 두고, 비인물 판정(노출, 선명도)만 적용한다. 이유는 리포트에 "얼굴 없음"으로 남긴다 |
| 7 | **눈 감김(B)인데 얼굴을 못 찾은 컷은 0장**이다 (47/47, 1/1). 다만 표본이 라벨 있는 컷뿐이라, 옆모습·작은 얼굴에서의 검출은 아직 검증되지 않았다 | T1.5(판정 불가 분리)에서 얼굴 크기·yaw별 성능을 본다 |
| 8 | pyobjc 라이선스를 확인하지 않았다 | **[미확인]** 프로젝트 의존성에 넣기 전에 확인 |
