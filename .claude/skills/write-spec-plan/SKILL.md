# write-spec-plan

기획 문서를 개발할 수 있는 문서 두 개로 바꾼다.

- **spec.md**: 무엇을, 왜 만드는가. 6칸. **기술 이름을 쓰지 않는다.**
- **plan.md**: 어떻게 만드는가. 5칸. **spec.md에 없는 요구사항을 새로 만들지 않는다.**

형식은 [references/spec-template.md](references/spec-template.md), [references/plan-template.md](references/plan-template.md)를 따른다. 사용자는 한국어를 쓰고 쉬운 말을 원한다.

## 0. 시작하기 전에 읽는다 (순서대로)

1. `Intent.md` — 현재 작업의 문제·기대 결과·영향 범위·제약·열린 질문
2. `IA.md` → `uj.md` → `PRD.md` → `erd.md` → `GLOSSARY.md` → `docs/adr/`
3. 기존 `spec.md`, `plan.md`가 있으면 **먼저 읽고 고친다.** 새로 덮어쓰지 않는다

Intent.md가 이 작업을 가리키지 않으면 먼저 Intent.md부터 갱신한다.

## 1. 모르는 것은 묻는다

- 문서에 답이 없는 결정은 지어내지 않는다. 쉬운 말로 선택지와 결과를 설명하고 **추천을 붙여** 묻는다 (`grill-with-docs` 방식: 한 번에 여러 질문, 각 질문에 추천 답, 사용자가 "응"이면 추천 수락).
- 확인할 수 없는 것은 **[확인 필요]**로 표시하고 spec.md 6칸에 남긴다.
- 사용자가 정한 것은 **[확정]**, 내가 정한 것은 **[제안]**, 근거 없는 전제는 **[가정]**으로 구분해서 쓴다.

## 2. spec.md 쓰기 (6칸)

| 칸 | 쓰는 법 |
|---|---|
| 1. 해결하려는 문제 | 이 기능이 없어서 지금 **무엇이 막히는지**. "지금은 어떻게 하나"와 근거(Intent·인터뷰)를 표로 |
| 2. 주요 사용자 | **누가, 어떤 장면에서** 쓰는지. 장면을 A, B, C…로 나눈다 |
| 3. 핵심 기능과 요구사항 | **번호를 붙인다.** PRD의 FR 번호를 그대로 쓴다(번호 체계를 두 개 만들지 않는다). MUST/SHOULD로 중요도 표시. **요구사항마다 "확인"을 붙인다: Given 이런 상태에서 / When 이렇게 하면 / Then 이렇게 보인다.** 예외 상황, 다루는 데이터(ERD 이름), 행동 규칙(항상 / 먼저 물어보기 / 절대 안 함)을 하위 항목으로 |
| 4. 성공 기준 | **"끝"의 정의.** 눈으로 확인할 수 있게, 번호(SC-01…)를 붙이고 수치가 있으면 단위까지. 수치가 근거 없으면 [제안]으로 표시하고 측정 후 확정한다 |
| 5. 제외 범위 | 이번에 **일부러** 안 만드는 것과 이유, 어디서 다루는지 |
| 6. 확인 필요 사항 | 아직 못 정한 것. 구현 전에 정할 것은 ★. 정하는 방법과 영향 |

규칙
- 기술 이름(언어, 라이브러리, 파일명)은 spec.md에 쓰지 않는다. 쓸 수 있는 건 사용자가 보는 것과 데이터 이름(ERD)뿐이다.
- 요구사항 하나는 한 가지만 말한다. "그리고"로 이어진 두 기능은 나눈다.
- 모호한 말("빠르게", "쉽게")은 숫자나 눈으로 보이는 결과로 바꾼다. 못 바꾸면 [확인 필요].
- 용어는 GLOSSARY.md와 IA 용어 규칙을 따른다. 금지어는 화면 문구에 쓰지 않는다.
- 성공 기준의 모든 항목이 최소 하나의 FR과 연결되고, 모든 MUST FR이 최소 하나의 SC나 "확인"으로 닫힌다.

## 3. plan.md 쓰기 (5칸)

| 칸 | 쓰는 법 |
|---|---|
| 1. 기술과 버전 | 표: 영역 / 기술 / **정확한 버전** / 출처. **버전은 기억이 아니라 잠금 파일(`requirements-lock.txt`, `package.json` 등)과 설치된 환경(`pip list`, 실행 결과)에서 읽는다.** 출처 칸에 어디서 읽었는지 쓴다. **새 라이브러리는 기본 0개.** 필요하면 멈추고 이유·더 단순한 대안·공식 문서의 현재 버전을 적어 사용자에게 먼저 묻는다 |
| 2. 구조와 파일 | **실제 저장소를 `ls`로 확인한** 폴더·파일 표: 지금 하는 일 / 이번에 (수정·신규·변경 없음) / 관련 FR. 없는 파일은 "신규"로 표시. 표 모양은 `erd.md`에서 가져온다. 저장 위치·API·화면 구성(IA 화면 ID)을 함께. 건드리면 안 되는 파일(동결 코드)을 명시 |
| 3. 단계별 접근 | 단계마다: 만드는 것 / 바꾸는 파일 / **끝났다고 보는 기준(SC 번호)** / **되돌리는 방법.** 단계마다 기존 테스트가 통과해야 다음으로 간다. 새 라이브러리·예외를 들이면 "복잡도 기록"에 이유 |
| 4. 테스트 전략 | **성공 기준(SC)마다 확인 수단 하나 이상**: 함수 시험, 서버 시험, 안전 시험, 회귀, 화면 눌러 보기, 성능 측정, 사람이 직접(QA 시트), DB 시험. 에이전트가 직접 못 보는 것(예: 앱 창 안)은 "사람이 확인"으로 분명히 쓴다 |
| 5. 제약과 주의점 | 비밀 키 노출 금지, 속도, **지금 돌아가는 기능 깨지 않기**, 동결 코드, 삭제 금지, 네트워크 규칙, 환경 주의. 위험은 표(가능성·영향·대응). 확인 필요는 spec 번호와 같게 |

규칙
- plan.md에서 요구사항을 추가·변경하지 않는다. 필요하면 spec.md를 먼저 고친다.
- 파일·함수 이름은 저장소에서 확인한 것만 "수정"으로 쓴다. 확인 못 하면 [확인 필요].
- 마지막에 **추적표** (FR → 단계 → 주 파일 → 시험)를 둔다.

## 4. 마치기 전에 점검한다

- [ ] spec의 모든 FR이 plan 단계와 시험에 연결되어 있다 (추적표)
- [ ] spec의 모든 SC에 plan 4장의 확인 수단이 있다
- [ ] plan의 모든 "수정" 파일이 실제로 있고, "신규"는 아직 없다
- [ ] plan의 버전이 잠금 파일·설치 환경과 같다
- [ ] spec에 기술 이름이 없다
- [ ] 확인 필요 번호가 spec과 plan에서 같다
- [ ] 용어가 GLOSSARY와 같고 금지어가 없다
- [ ] 동결 코드와 삭제 금지가 제약에 있다
- [ ] 비밀 키 노출 금지가 plan 5칸에 있다

## 5. 문서도 같이 맞춘다

- `Intent.md`의 참조 문서와 작업 이력에 spec.md·plan.md를 연결한다.
- PRD·IA·ERD와 어긋난 곳은 이번 작업에서 같이 고치고, 못 고친 것은 사용자에게 알린다.
- 새 용어는 GLOSSARY에, 되돌리기 어려운 결정은 ADR로.
- **커밋·푸시는 사용자가 시켰을 때만 한다.** 푸시하면 Vercel이 자동 배포한다.

## 6. 결과를 보고할 때

- 만든 파일, 사용자가 확인해야 할 [제안]과 ★ 확인 필요, 확인하지 못한 것(제가 직접 못 본 것)을 쉬운 말로 알린다.
- 웹 자료를 참고했으면 출처를 밝히고, 공식 문서를 직접 읽지 못한 것은 그렇게 말한다.
